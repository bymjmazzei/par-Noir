FIELD OF THE INVENTION
The present invention relates generally to computer-implemented identity management, cryptographic recovery, user-controlled cloud storage, and content aggregation. More particularly, embodiments relate to a portable post-quantum identity artifact, a recovery vault configured on user-owned cloud storage operating under a threshold custodian policy that includes protected custodians, a dual-path identity continuity framework distinguishing same-key recovery from full cryptographic re-key with network succession, and a public content aggregator whose membership truth is defined by a user-authored index periodically reconciled against a server performance cache.

BACKGROUND OF THE INVENTION
Traditional digital identity architectures heavily rely on centralized database systems operated by third-party identity providers. Under these frameworks, users do not own or possess their authoritative core identity artifacts; instead, they depend on external registration authorities to issue identifiers, maintain state metadata, and mediate recovery processes via administrative mechanisms such as email resets or human help desks.

Recent advancements have introduced cryptographic wallets and self-sovereign identity (SSI) models leveraging decentralized identifiers (DIDs). However, these systems focus primarily on securing blockchain private keys or ledger-anchored DID documents. They fail to integrate identity protocol mechanics with structured user-owned consumer cloud layouts spanning local client applications, private data repositories, and dynamically generated public indexes.

Furthermore, existing social recovery methods (such as those using Shamir's secret sharing shards) typically rely on an arbitrary M-of-N quorum of contacts, or rely on hardware security modules (HSMs) managed by a service provider. In these ecosystems, an identity owner maintains absolute, unchecked supremacy to revoke or alter any custodian at will. While this maximizes owner control, it exposes the system to vulnerabilities if the owner's client device is entirely compromised, as a malicious actor can systematically revoke valid custodians to lock out the legitimate owner. Prior art systems do not provide a mechanism where a specific class of custodian is explicitly rendered unrevokable within a user-owned vault to enforce structural recovery guardrails.

Similarly, conventional content platforms aggregate public feeds by drawing membership sets directly from operator-controlled databases. When a user revokes visibility or deletes a file on their end, the operator database may remain stale. While personal-data vault systems have attempted to aggregate private data into user-controlled storage, they do not treat a user-authored spreadsheet index on a commodity cloud drive as the absolute authority for public feed membership. Accordingly, there is a distinct technical need for an identity and data indexing architecture that operates completely independent of centralized databases, establishing the user's personal cloud infrastructure as the single source of truth for protocol logic, data routing, and identity recovery.

SUMMARY OF THE INVENTION
To address the limitations of prior systems, the present invention provides a computer-implemented protocol that shifts data ownership and logical authority directly to user-managed environments.

In a first aspect, an identity recovery system comprises a processor and a non-transitory storage medium storing instructions to maintain a portable identity file containing a post-quantum identity payload, a recovery envelope, and passcode-sealed Shamir shares. The system maintains a structured recovery vault directly within user-controlled cloud storage. Upon initialization of a recovery request, the system evaluates incoming approval payloads against a strict quorum rule. The quorum rule structurally demands both a threshold number of total approvals and at least one explicit approval from a specific custodian designated as unrevokable in the recovery vault database. Once satisfied, the system combines the shares to reconstruct a recovery master secret, computes a SHA-256 key digest over the recovery master secret, decrypts the recovery envelope via AES-GCM, and re-encrypts the identity payload with a new passcode while preserving the underlying public key.

In a second aspect, a computer-implemented method coordinates an alternative path of identity continuity via cryptographic re-key migration. The method generates a successor post-quantum key pair distinct from a compromised predecessor key pair. Rather than breaking links to existing storage data, the method pins the unique identifier of the user's cloud folder in storage credentials, executes an in-place migration to re-wrap encrypted files, direct messages, and group keys, modifies identifier strings within spreadsheet indexes, generates a dual-signed lineage zero-knowledge proof binding the keys, and registers an online network succession record. The succession record causes network servers to aggressively reject the predecessor for online operations (such as OAuth tokens and feed ingestion) while explicitly permitting the predecessor file to remain decryptable offline locally.

In a third aspect, an aggregation system features a non-authoritative server-side cache that handles query delivery to browser clients without owning membership truth. A background reconcile module periodically authenticates into the user-controlled cloud storage using per-user credentials, reads a user-authored public file index, and removes cache entries whose identifiers are absent from the index. When a user executes an explicit deletion via application or API channels, the user-authored index is updated, triggering an immediate cache purge without awaiting the periodic reconcile loop. If a network authentication error occurs during the loop, the system skips that user entirely to prevent accidental mass purges due to transient connectivity drops.

DETAILED DESCRIPTION OF PREFERRED EMBODIMENTS
Referring to FIG. 1, the overall system architecture comprises a user device 100 running a specialized pN client application 102. The user device 100 holds a portable digital identity file 104 locally. A user-controlled cloud storage instance 110 (such as a consumer drive account linked via OAuth) communicates with a coordinating API server 120. Client application 102 interacts with server 120 via API endpoints, while specialized client views may optionally maintain direct read/write storage access to user cloud 110. The API server 120 maintains an OAuth client registry 122 for third-party integrators 150 but does not store identity private keys, names, or passcodes. An aggregator cache database 130 acts as a high-performance metadata engine, which is accessed by an aggregator browser client 140.

Identity Generation and Three-Factor Structure
As shown in FIG. 2, creating an identity begins when a user inputs a name string and a passcode at step 200. The client application 102 executes post-quantum key generation at step 202 to generate an ML-DSA-65 signing key pair and an ML-KEM-768 encapsulation key pair. At step 204, the private key components are wrapped into a JSON string and encrypted via AES-GCM using a key derived from the name and passcode via PBKDF2 with at least one million iterations and a SHA-512 hashing policy.

A random 32-byte recovery master secret R is generated at step 206 and split via a threshold Shamir secret sharing scheme. At step 208, a key digest SHA-256(R) is derived from the recovery master secret R, and core identity metadata is encrypted with SHA-256(R) using AES-GCM to form a recovery envelope 209. Crucially, the generated Shamir shares are themselves sealed into a distinct data block within the identity file 104 using a separate AES-GCM key derived from the user's name and passcode factors via PBKDF2 with SHA-512 and at least one million iterations at step 210. The finished portable identity file 104 is exported at step 212.

Unlock mechanics are mapped in FIG. 3. To gain execution capabilities, the user must present the physical identity file 104, the name string, and the passcode together at step 300. The client derives the key material at step 302 and decrypts the core identity payload at step 304. If any single factor is missing or modified, decryption fails, and the system aborts operations at step 306.

The Cloud-Resident Recovery Vault and Quorum Logic
FIG. 4 outlines the state structure of the recovery vault 400 configured directly as a structured spreadsheet file (recovery.xlsx) inside a metadata directory on the user's cloud storage 110. The sheet comprises a PendingShares table 402 and a Custodians table 404. Each row in the Custodians table tracks fields including a custodian identifier, a share index, a zero-knowledge custodianship credential string, a registration status (selected from invited, accepted, or revoked), and an unrevokable configuration flag 406.

The system enforces an explicit programmatic barrier at the API data processing layer: when the API server 120 or client application 102 processes a request to update vault state, any request targeting a custodian entry where the unrevokable flag 406 is true causes the API server 120 to reject the modification transaction, ensuring that at least one protected custodian remains permanently active within the vault.

The mathematical confirmation of recovery follows the sequence diagram in FIG. 5. The owner issues a custodianship zero-knowledge envelope 500 containing an outer ML-DSA signature binding the public key, custodian identifier, and threshold parameters over an inner STARK proof. During an active recovery request 504, the participating custodian generates an approval zero-knowledge envelope 506 containing an explicit intent string and request identifier. The combined payload 508 is delivered to the coordinating API 120, which evaluates the recovery ready condition 408 at step 510. The recovery ready condition is true if and only if the count of accepted approvals meets or exceeds the threshold T, and at least one accepted approval corresponds to a custodian marked as unrevokable.

If a recovery sequence attempts to compile shares without including the unrevokable custodian's proof payload, the API blocks reconstruction. Once satisfied (FIG. 6), the gathered shares are combined to reconstruct the recovery master secret R at step 604. The system computes a key digest SHA-256(R) to derive the decryption key, which decrypts the recovery envelope via AES-GCM at step 606. The system verifies that the decrypted public key matches the public key embedded in the file 104 at step 608. The user inputs a new passcode factor at step 610, and the system re-encrypts the identity payload at step 612 while maintaining the exact same public key, preserving existing network identifiers.

Pinned Storage Migration and Identity Succession
FIG. 7 maps the re-key migration pipeline, which provides a non-destructive key rotation path. When a user triggers rotation at step 700, the client application 102 generates a brand-new, distinct successor post-quantum key pair at step 702. Rather than provisioning a new storage folder, the system pins the unique drive folder identifier 704 within its storage token metadata. The system then drives an automated file migration loop within the folder, which sequentially re-wraps encrypted objects, direct messages, and group keys using the successor public key at step 708, updates internal text rows inside the public and owner index spreadsheets at step 710, re-invites custodians, re-issues active zero-knowledge proofs, and generates a lineage zero-knowledge proof binding the old public key and new public key together at step 714.

The folder is renamed to match the successor identifier string at step 716. Finally, the system registers the transaction with the server at step 718 to produce the asymmetrical network succession effects illustrated in FIG. 8. Online network entities check the server succession endpoint 806. Consequently, any attempt to use the predecessor identifier 800 to request OAuth authorization codes, refresh tokens, or ingest new public feed posts is actively rejected. However, the physical predecessor identity file remains fully capable of local, offline decryption 804, permitting data visibility without offering an active network exploitation surface.

Reconciled Public Aggregation Loop
The structure of the user-controlled folder layout is itemized in FIG. 9, showing the placement of the public file index spreadsheet 112 (public-file-index.xlsx) under the root metadata directory. This index file 112 serves as the absolute authority for feed membership.

FIG. 10 outlines the background execution of the reconcile module 124. The reconcile job wakes up on a continuous five-minute interval at step 1000. For each active user identifier tracked in the server-side performance cache database 130 (step 1002), the module reads the public index spreadsheet 112 from the user's cloud account using credentialed OAuth tokens at step 1004.

The logic evaluates the cache membership: if a specific file identifier exists inside the server-side database 130 but is completely missing from the user's cloud index spreadsheet 112, the module purges that metadata entry from the performance cache at step 1008. When an explicit file deletion is initiated via client application or API pathways, the index sheet is updated and an immediate cache purge call is dispatched to update database 130 without delay. If the user has completely deleted the index sheet, the reconcile loop executes a total purge of that user's cached rows at step 1006. Crucially, if the cloud provider API returns an explicit authentication error code (such as an expired token or a temporary credential disruption), the loop aborts and skips that user entirely at step 1010. This ensures that network connection drops do not trigger false-positive purges of a user's public feed metadata.

Integrator Silo and Storage Confinement
FIG. 11 illustrates the execution of an integrator silo provisioning mechanism. When a third-party integrator 150 registers an OAuth client identifier 152 with the coordinating API server 120 and receives a user storage grant, the system provisions a dedicated folder under the user-controlled cloud storage 110 identified as integrators/{client_id}/. A storage proxy 154 restricts storage API read, write, and delete requests from the integrator 150 strictly to paths within that dedicated folder. Standard identity data point proofs remain stored in a metadata spreadsheet separate from the dedicated integrator folder and are accessible to the integrator only via dedicated proof API endpoints 156 governed by a permissions sheet on the user-controlled cloud storage 110.

Zero-Knowledge Envelope Structure
FIG. 12 illustrates the structural schema of a version 2 zero-knowledge proof envelope 1200 used for custodianship, recovery approvals, and selective disclosure data points. The envelope 1200 encodes a format version (with version 1 proofs supported for legacy verification), a proof type identifier specifying a STARK inner proof with an outer post-quantum signature binding, a hash policy identifier specifying SHA3-384, canonical public inputs, a context string, a nonce, an expiration timestamp, an inner STARK proof payload, and an outer ML-DSA signature binding the public key over a SHA3-384 binding digest of the envelope fields.

Selective Disclosure via Broker Entities
FIG. 13 depicts the sequence flow for user-sovereign selective disclosure mediated through an OAuth-registered integrator 150 (or preferred broker entities 158 such as data unions or data exchanges). Upon receiving an authorization grant 1300 from a user device 100, the API 120 writes a permission row to a permissions spreadsheet 160 on the user-controlled cloud storage 110. When an OAuth integrator 150 submits a proof request 1302 to the proof API 156, the API reads the permissions sheet 160 from the user cloud storage 110. If the grant is active, the API retrieves a matching zero-knowledge proof envelope from a data-points store 162 on the user cloud storage 110, verifies its binding digest and expiry, and returns the proof envelope 1308 to the integrator 150. The integrator relays the proof to a verifier 159 without receiving a pN name, a passcode, private keys, or underlying plaintext sensitive attributes.
