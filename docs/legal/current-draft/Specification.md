FIELD OF THE INVENTION
The present invention relates generally to computer-implemented identity management, cryptographic recovery, user-controlled cloud storage, and content aggregation. More particularly, embodiments relate to a portable post-quantum identity artifact, a recovery vault configured on user-owned cloud storage operating under a threshold custodian policy that includes protected custodians, a dual-path identity continuity framework distinguishing same-key recovery from full cryptographic re-key with network succession, and a public content aggregator whose membership truth is defined by a user-authored index structure periodically reconciled against a server performance cache.

BACKGROUND OF THE INVENTION
Traditional digital identity architectures heavily rely on centralized database systems operated by third-party identity providers. Under these frameworks, users do not own or possess their authoritative core identity artifacts; instead, they depend on external registration authorities to issue identifiers, maintain state metadata, and mediate recovery processes via administrative mechanisms such as email resets or human help desks.

Recent advancements have introduced cryptographic wallets and self-sovereign identity (SSI) models leveraging decentralized identifiers (DIDs). However, these systems focus primarily on securing blockchain private keys or ledger-anchored DID documents. They fail to integrate identity protocol mechanics with structured user-owned consumer cloud layouts spanning local client applications, private data repositories, and dynamically generated public indexes.

Furthermore, existing social recovery methods (such as those using Shamir's secret sharing shards) typically rely on an arbitrary M-of-N quorum of contacts, or rely on hardware security modules (HSMs) managed by a service provider. In these ecosystems, an identity owner maintains absolute, unchecked supremacy to revoke or alter any custodian at will. While this maximizes owner control, it exposes the system to vulnerabilities if the owner's client device is entirely compromised, as a malicious actor can systematically revoke valid custodians to lock out the legitimate owner. Prior art systems do not provide a mechanism where a specific class of custodian is explicitly rendered unrevokable within a user-owned vault structure to enforce structural recovery guardrails.

Similarly, conventional content platforms aggregate public feeds by drawing membership sets directly from operator-controlled databases. When a user revokes visibility or deletes a file on their end, the operator database may remain stale. While personal-data vault systems have attempted to aggregate private data into user-controlled storage, they do not treat a user-authored index structure on a commodity cloud drive as the absolute authority for public feed membership. Accordingly, there is a distinct technical need for an identity and data indexing architecture where user-authored cloud structures serve as authoritative for designated protocol state (such as public index membership and recovery vault ledgers), while operator systems provide non-authoritative performance caching and network coordination services.

SUMMARY OF THE INVENTION
To address the limitations of prior systems, the present invention provides a computer-implemented protocol that shifts data ownership and logical authority directly to user-managed environments, establishing that user-controlled cloud storage structures act as authoritative for designated protocol state (including recovery vault ledgers and public index membership) while operator infrastructure handles non-authoritative performance caching, client registries, and network coordination.

In a first aspect, an identity recovery system comprises a processor and a non-transitory storage medium storing instructions to maintain a portable identity file comprising cleartext post-quantum public key material, an encrypted identity payload, a recovery envelope, and passcode-sealed cryptographic shares. The system maintains a structured recovery vault directly within user-controlled cloud storage. Upon initialization of a recovery request, the system evaluates incoming approval payloads against a strict quorum rule. The quorum rule structurally demands both a threshold number of total approvals and at least one explicit approval from a specific custodian designated as unrevokable in the recovery vault structure. Once satisfied, the system combines the shares to reconstruct a recovery master secret, derives a decryption key from the recovery master secret, decrypts the recovery envelope to extract the public key, and re-encrypts the identity payload under a new passcode factor while preserving the underlying public key.

In a second aspect, a computer-implemented method coordinates an alternative path of identity continuity via cryptographic re-key migration. The method generates a successor post-quantum key pair distinct from a compromised predecessor key pair. Rather than breaking links to existing storage data, the method pins the unique identifier of the user's cloud folder in storage credentials, executes an in-place migration to re-wrap encrypted digital assets (such as files, direct messages, and group keys) under the successor public key, modifies identifier strings within index structures, generates a dual-signed lineage zero-knowledge proof binding the keys, and registers an online network succession record. The succession record causes network servers to reject online operations presenting the predecessor key pair (including token authorizations, feed ingestion, and network-backed features) while explicitly permitting the predecessor file to remain decryptable offline locally.

In a third aspect, an aggregation system features a non-authoritative server-side performance cache that handles query delivery to browser clients without owning membership truth. Long-lived cloud authorization secrets remain on the user device; the cache is aligned with the user-authored public index via owner publish of public content, explicit deletion commands that trigger immediate cache purge, dead-link clearing when public-content retrieval fails, and owner-device reconcile that reads the public index using a cloud access token forwarded from the user device. If a network authentication error occurs during an index read, the system skips that user entirely to prevent accidental mass purges due to transient connectivity drops.

DETAILED DESCRIPTION OF PREFERRED EMBODIMENTS
Referring to FIG. 1, the overall system architecture comprises a user device 100 running a specialized pN client application 102. The user device 100 holds a portable digital identity file 104 locally. A user-controlled cloud storage instance 110 (such as a consumer drive account linked via a delegated authorization protocol like OAuth) is accessed through a coordinating API server 120. In a preferred embodiment, long-lived cloud authorization secrets for cloud 110 are retained on user device 100 (for example, sealed in a device-held credential vault), and client application 102 forwards an ephemeral cloud access token to API server 120 for owner storage operations; API server 120 does not retain those long-lived cloud OAuth secrets. Client application 102 interacts with server 120 via API endpoints. Aggregator browser client 140 accesses feeds and storage exclusively through API server 120 (no direct cloud-provider API). The API server 120 maintains an authorization client registry 122 for authorized client entities 150 (such as third-party integrators or data brokers) but does not store identity private keys, names, or passcodes. User-controlled cloud storage structures act as authoritative for designated protocol state (such as public index membership and recovery vault ledgers), while operator systems provide non-authoritative performance caching and coordination services. An aggregator cache database 130 acts as a non-authoritative, high-performance metadata engine accessed by aggregator browser client 140. Membership alignment module 124 keeps cache 130 consistent with public index 112 as described with reference to FIG. 10.

Identity Generation and Three-Factor Structure
As shown in FIG. 2, creating an identity begins when a user inputs a user identifier (such as a name string) and a passcode factor at step 200. The client application 102 executes post-quantum key generation at step 202 to generate cleartext public key material (such as an ML-DSA-65 signing public key and an ML-KEM-768 encapsulation public key) and matching private key components. At step 204, the private key components are wrapped into a structured data payload (such as a JSON string, CBOR payload, or binary data structure) and encrypted via authenticated symmetric encryption (such as AES-GCM) using a key derived from the user identifier and passcode via a key derivation function (such as PBKDF2 with at least one million iterations and a SHA-512 hashing policy). The cleartext public key material remains stored outside the encrypted payload on the portable identity file 104, permitting client inspection without requiring decryption.

A random 32-byte recovery master secret R is generated at step 206 and split via a threshold secret sharing scheme (such as Shamir's secret sharing). At step 208, a key digest SHA-256(R) is derived from the recovery master secret R, and core identity metadata is encrypted with SHA-256(R) using AES-GCM to form a recovery envelope 209. Crucially, the generated secret shares are themselves sealed into a distinct data block within the identity file 104 using a separate AES-GCM key derived from the user's name and passcode factors via PBKDF2 with SHA-512 and at least one million iterations at step 210. The finished portable identity file 104 is exported at step 212.

Unlock mechanics are mapped in FIG. 3. To gain execution capabilities, the user must present the physical identity file 104, the user identifier, and the passcode factor together at step 300. The client derives the key material at step 302 and decrypts the core identity payload at step 304. If any single factor is missing or modified, decryption fails, and the system aborts operations at step 306.

The Cloud-Resident Recovery Vault and Quorum Logic
FIG. 4 outlines the state structure of the recovery vault 400 configured directly as a structured index structure, file, or spreadsheet (e.g., recovery.xlsx) inside a metadata directory on the user's cloud storage 110. The sheet comprises a PendingShares table 402 and a Custodians table 404. Each row in the Custodians table tracks fields including a custodian identifier, a share index, a zero-knowledge custodianship credential string, a registration status (selected from invited, accepted, or revoked), and an unrevokable configuration flag 406.

The system enforces an explicit programmatic barrier at the protocol execution layer: when the API server 120 or client application 102 processes a request targeting vault state, any revocation request targeting a custodian entry where the unrevokable flag 406 is true causes the API server 120 to reject the revocation transaction, ensuring that at least one protected custodian remains permanently active within the vault. Non-revocation state updates (such as custodian acceptance flows) remain permitted.

The mathematical confirmation of recovery follows the sequence diagram in FIG. 5. The owner issues a custodianship zero-knowledge envelope 500 containing an outer ML-DSA signature binding the public key, custodian identifier, and threshold parameters over an inner STARK proof. During an active recovery request 504, the participating custodian generates an approval zero-knowledge envelope 506 containing an explicit intent string and request identifier. The combined payload 508 is delivered to the coordinating API 120, which evaluates the recovery ready condition 408 at step 510. The recovery ready condition is true if and only if the count of accepted approvals meets or exceeds the threshold T, and at least one accepted approval corresponds to a custodian marked as unrevokable.

If a recovery sequence attempts to compile shares without including the unrevokable custodian's proof payload, the API blocks reconstruction. Once satisfied (FIG. 6), the gathered shares are combined to reconstruct the recovery master secret R at step 604. The system computes a key digest SHA-256(R) to derive the decryption key, which decrypts the recovery envelope via AES-GCM at step 606 to extract the public key. The system verifies that the decrypted public key matches the cleartext public key embedded in the file 104 at step 608. The user inputs a new passcode factor at step 610, and the system re-encrypts the identity payload at step 612 while maintaining the exact same public key, preserving existing network identifiers.

Pinned Storage Migration and Identity Succession
FIG. 7 maps the re-key migration pipeline, which provides a non-destructive key rotation path. When a user triggers rotation at step 700, the client application 102 generates a brand-new, distinct successor key pair at step 702. Rather than provisioning a new storage folder, the system pins the unique drive folder identifier 704 within its storage token metadata. The system then drives an automated file migration loop within the folder, which sequentially re-wraps encrypted digital assets (including data files, direct messages, and group keys) using the successor public key at step 708, updates internal text rows inside the public and owner index structures (such as spreadsheets) at step 710, updates user permissions structures during folder migration, re-invites custodians, re-issues active zero-knowledge proofs, and generates a lineage zero-knowledge proof binding the old public key and new public key together at step 714.

The folder is renamed to match the successor identifier string at step 716. Finally, the system registers the transaction with the server at step 718, updating owned-asset references upon registration to produce the asymmetrical network succession effects illustrated in FIG. 8. Online network entities check the server succession endpoint 806. Consequently, any attempt to use the predecessor identifier 800 for online token authorizations, feed ingestion, or network-backed operations is actively rejected. However, the physical predecessor identity file remains fully capable of local, offline decryption 804, permitting data visibility without offering an active network exploitation surface.

Reconciled Public Aggregation Loop
The structure of the user-controlled folder layout is itemized in FIG. 9, showing the placement of the public file index structure 112 (e.g., public-file-index.xlsx) under the root metadata directory. This index structure 112 serves as the absolute authority for feed membership because user cloud storage acts as authoritative for public index membership state, reducing server-side caches to disposable, non-authoritative performance layers. FIG. 9 further shows an on-demand messaging tree under par-noir-messages/, including a sender-owned _outbox/ subdirectory used as a durable commit for private peer delivery under device-cloud custody. Peer conversation materialization into the recipient's own cloud occurs on the recipient device after opaque throughway delivery; senders do not perform cross-user writes into another user's cloud using peer credentials.

FIG. 10 outlines membership alignment for aggregator cache 130 relative to public index 112. The coordinating server does not crawl private clouds with stored OAuth secrets. Instead: (a) owner publish of public content pushes catalog metadata and a public-content reference into cache 130; (b) an explicit file deletion via client application or API pathways updates index structure 112 and dispatches an immediate cache purge to database 130 without awaiting a background interval; (c) dead-link clearing occurs when a public-content retrieval for a cached file identifier returns a not-found or gone status, causing removal of the corresponding cache row; and (d) owner-device reconcile, after unlock or drive layout readiness, reads public index 112 (and/or verifies public blobs) using a cloud access token forwarded from user device 100 and removes cache entries whose unique identifiers are absent from authorized public membership (steps 1002–1008). If an index or blob read returns an explicit authentication error, that user's removal pass is skipped (step 1010). Aggregator browser 140 reads cache 130 via API 120 at step 1012.

Integrator Silo and Storage Confinement
FIG. 11 illustrates the execution of an integrator silo provisioning mechanism. When an authorized client entity 150 registers a client identifier 152 with the coordinating API server 120 and receives a user storage grant, the system provisions a dedicated client storage folder under the user-controlled cloud storage 110 (such as a folder identified as integrators/{client_id}/). A storage proxy 154 restricts storage API read, write, and delete requests from the authorized client entity 150 strictly to paths within that dedicated folder. Standard identity data point proofs remain stored in a metadata structure separate from the dedicated client storage folder and are accessible to the authorized client entity only via dedicated proof API endpoints 156 governed by a permissions sheet or index on the user-controlled cloud storage 110.

Zero-Knowledge Envelope Structure
FIG. 12 illustrates the structural schema of a zero-knowledge proof envelope 1200 used for custodianship, recovery approvals, and selective disclosure data points. The envelope 1200 encodes a format version (with legacy versions supported for verification), a proof type identifier specifying a STARK inner proof with an outer post-quantum signature binding, a cryptographic hash policy (such as SHA3-384), canonical public inputs, a context string, a nonce, an expiration timestamp, an inner STARK proof payload, and an outer post-quantum signature (such as ML-DSA) binding the public key over a digest of the envelope fields.

Selective Disclosure via Broker Entities
FIG. 13 depicts the sequence flow for user-sovereign selective disclosure mediated through an authorized client entity 150 or broker entity 158. Upon receiving an authorization grant 1300 from a user device 100, the API 120 writes a permission row to a permissions structure 160 on the user-controlled cloud storage 110. When an authorized client entity 150 submits a proof request 1302 to the proof API 156, the API reads the permissions structure 160 from the user cloud storage 110. If the grant is active, the API retrieves a matching zero-knowledge proof envelope from a data-points store 162 on the user cloud storage 110, verifies its binding digest and expiry, and returns the proof envelope 1308 to the authorized client entity 150. The authorized client entity relays the proof to a verifier 159 without receiving a user identifier, a passcode, private keys, or underlying plaintext sensitive attributes.

OAuth Unlock Proof Embodiment
In some embodiments, minting a network authorization session (for example, an OAuth authorization code or access token bound to the identity public key) requires a challenge-bound post-quantum signature (such as ML-DSA-65) produced only after three-factor unlock of portable identity file 104 on user device 100. The unlock factors (user identifier string and passcode factor) are not transmitted to API server 120 on the authenticate path; the server verifies possession of the signing secret via the unlock proof. This embodiment reinforces that API 120 does not receive or store unlock secrets.

Sealed Cloud Credential Vault Embodiment
In some embodiments, first-party clients seal cloud authorization material (such as provider access and refresh tokens) into a device-held vault using a key encapsulation secret derived from the unlocked identity (for example, ML-KEM). After unlock, a client unseals the vault and forwards an ephemeral cloud access token to API 120 for owner Drive operations, enabling cross-app hydrate without the coordinating server retaining long-lived cloud OAuth secrets.
